# 0134. The app's capabilities on Windows

Status: accepted, 2026-11-17. Builds on [0125](0125-the-app-runs-on-windows.md) (the app on Windows), whose stand-ins it replaces one capability at a time; amends it.

## Context
ADR 0125 got the app running on Windows with most capabilities off: each a stand-in in its `<capability>_windows.dart`. What each needs from Windows is a call through `dart:ffi` (user32, shell32, COM), so the runner stays without a channel of its own where it can; WebView2 can't be reached that way (its controllers are made and called back on the window's thread, through COM handlers), so web views are the one capability the runner holds.

## Decision
- **The clipboard**: read in-process through user32, opened and closed in one synchronous call on an isolate of its own, never the window's: a format an app renders only when asked keeps `GetClipboardData` waiting on that app (for good if it hangs), so a paste that waits more than 5 s gets nothing. Files are `CF_HDROP`'s paths (`DragQueryFileW`). A picture, only when the clipboard holds no text (as on the Mac), is the PNG an app registered (`PNG`, a browser's copied image) as it is, else the bitmap (`CF_DIB`, which a screenshot is and Windows makes of any other) drawn as PNG by the engine: 24- and 32-bit pixels are read in Dart (a 32-bit one whose alpha is 0 everywhere is opaque, as apps that draw without alpha leave it), any other kind given to the engine as a BMP file.
- **Presenting the window**: the app's window is the runner's class's that this process made (`FindWindowExW`); it's restored if minimized and `SetForegroundWindow`ed. Windows grants the foreground only to a process that may take it (the user's last input, a notification's click), so where it refuses, the taskbar's button flashes until the window is chosen (`FlashWindowEx`), as a Linux desktop marks a window as wanting attention.
- **Spell check**: Windows's Spell Checking API (`ISpellChecker`, `spellcheck.h`), the checker its own text boxes use, through COM by FFI (each method by its vtable slot; no COM package), on the app's thread, whose apartment the runner set up. Its language is the user's locale's (`GetUserDefaultLocaleName`) among those it supports, else the first of that language; none, and there's no spell check. Ignore is its session's `Ignore`, Learn its `Add` (the user's dictionary for that language, shared by every app that checks with it).
- **Pages and diagrams in WebView2**: a small host in the runner (`windows/runner/web_views.cpp`, the `nushi/webview` channel), not a plugin: the maintained one (`webview_win_floating`) also registers a Linux implementation on WebKitGTK, which would change the Linux app's build and package, and fetches `nuget.exe` and a 2022 SDK at build time; the texture-based one (`webview_windows`) is unmaintained since 2024. The SDK's headers and static loader come from NuGet's package at a pinned version and SHA-256, downloaded by CMake into the build folder; the runtime is Windows's (Edge's). Each web view is a WebView2 controller, a child window of the Flutter view placed over the widget that holds its place (its rectangle after each frame, hidden while that widget's tickers are off, while anything a later overlay entry or overlay portal paints overlaps it, or once it's gone). It shows one page: any other main-frame navigation is cancelled, and one the user started (`IsUserInitiated`, a link or a new window) is opened in the default browser, as the Mac's preview does after a press; downloads are cancelled and every permission refused; no web messages or host objects, so nothing from a page reaches the app. They're in-private, in a profile of their own (`pages`), their data beside Nushi's data folder (`Nushi.WebView2`), not in it: Chromium gives its cache folders access entries of their own, and the daemon won't start on a folder with one (ADR 0124). A runtime that can't make an in-private one makes none (the page opens in the browser), as the Mac's preview loads nothing without its cookie rule. Three differences from the Mac's preview stay (`docs/roadmap.md`): cookies are kept for the profile while any web view is open (in-private, not blocked); the page's own script can read any file under its root, served as an https origin; and several navigations can leave within one click's activation window, where the Mac lets one out per press. A preview's root (the chat's folder, or the file's) is served as a host of its own (`p<hash>.nushi.example`, `SetVirtualHostNameToFolderMapping`), so the page reads files inside it and none outside, as WebKit's read access does. Mermaid's diagram pane is mermaid.html served the same way from the app's assets; the transcript's diagrams are drawn one at a time in one hidden web view, which takes no snapshot of itself, so the page draws each onto a canvas as PNG (labels as SVG text: HTML in a `foreignObject` would taint the canvas). Browser tabs aren't in it yet (`WebViews.embedded` stays false): they still open in the default browser.
- **Stopping the daemon**: a Windows Unix socket doesn't name the process at its other end, and a process with no console window has no SIGTERM, so the daemon says its pid in `Ping` (on the socket only, API 122) and makes an event, `Local\nushid-<pid>-stop`; set, it stops as on SIGTERM (agents, terminals and dev servers closed first). The app sets the event named by the pid its last ping gave (`AppInstall.stop`'s `pid`), with only `EVENT_MODIFY_STATE`; a daemon too old to say its pid isn't stopped, and the restart says to end it in Task Manager. An event of that name that exists before the daemon makes it is another process's, and the daemon doesn't watch it.

## Consequences
- Ctrl+V attaches Explorer's copied files and a pasted screenshot, as ⌘V does on the Mac.
- The composer checks spelling on Windows as on the Mac and Linux.
- A page's and a Mermaid file's preview, and the transcript's diagrams, show in the app on Windows; without the WebView2 runtime a page is the placeholder that opens it in the browser. Flutter can't draw over a child window, so a web view hides while anything an overlay draws (a dialog, the palette, a menu, a tooltip, a toast) covers part of it, and comes back once that goes.
- The first Windows build downloads WebView2's SDK (about 10 MB), which `docs/development.md` lists among the dependencies.
- Restart daemon is offered on Windows (`AppInstall.canStop`), as on the Mac and Linux, so a newer bundled daemon replaces the running one.
- A notification's click (once Windows has notifications) can bring the window up through `AppWindow.present`, as on Linux.

## Alternatives considered
- `CF_DIBV5` first: it carries alpha masks, but Windows synthesizes it from `CF_DIB` for most apps, and the engine's BMP reader takes either; `CF_DIB` is what every app's bitmap becomes.
- A runner channel in C++ (GDI+ to encode PNG; the spell checker's COM): more native code to build and test for what FFI and the engine's encoder do.
- `TerminateProcess` by the pid: simpler, but the daemon would end without closing its agents' sessions and terminals; a console control event needs the app to attach to the daemon's hidden console, which its agents share too.
- A web view rendered into a Flutter texture (as `webview_windows` does, through Windows.Graphics.Capture): Flutter could draw over it, but it's several times the C++, and capture has its own permissions and frame lag. A child window is what WebView2 does natively.
- `package:win32`'s COM bindings: a large dependency for the five methods the checker needs.

**Amendment (2026-11-20):** `AppInstall.canStop`, named under Consequences, is gone: with the stop event every platform stops its daemon, so it answered true everywhere, and Restart daemon now shows wherever the app has a packaged daemon (`restartsDaemon`; [ADR 0125](0125-the-app-runs-on-windows.md)'s amendment).
